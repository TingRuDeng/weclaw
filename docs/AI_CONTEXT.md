# WeClaw AI 上下文

## Project Snapshot

- 仓库类型：单一 Go 仓库，不是 coordination directory。
- Go 模块：`github.com/fastclaw-ai/weclaw`，以 `main.go` 和 `cmd/root.go` 进入 CLI。
- 产品定位：把微信个人号和飞书消息接入 AI Agent，业务层通过 `platform` 抽象隔离平台差异。
- 发布目标：`scripts/release.sh` 构建和发布 `darwin/arm64`、`linux/arm64`、`linux/amd64`，本机安装必须走 `weclaw update`；CI 额外交叉构建 `darwin/amd64` 作为兼容性检查，但正式和预发布 Release 不得上传该资产。发布门禁同时验证一键安装脚本，测试只能使用隔离的伪命令环境。GitHub Release 是版本和构建权威；公开并回下载验证后，`scripts/mirror_gitee_release.sh` 才通过外部 `GITEE_TOKEN` 把同一 main/tag、`weclaw_darwin_arm64` 与 `weclaw_linux_amd64` 的确定性 `.gz` 表示和包含三个正式资产的原始 `checksums.txt` 镜像到 Gitee，再从 `attach_files` 端点回下载、解压、逐一比较并校验原始摘要。安装器和更新器支持三个正式目标，其中 Gitee 提供 `darwin/arm64` 与 `linux/amd64`，`linux/arm64` 仍只使用 GitHub；Gitee 二进制附件执行有大小上限的解压，完整性仍以 GitHub 权威 `checksums.txt` 中的原始文件名为准。镜像脚本必须复用已有 Release、跳过已存在附件并为 curl 传输设置上限；`.github/workflows/mirror-gitee.yml` 只从既有 GitHub Release 下载权威资产，用于失败后的幂等续传。镜像失败不得清理已提交的 GitHub Release，但必须让发布任务可观察地失败。`.github/workflows/release.yml` 只负责从 `main` 调用该权威脚本，不得复制一套较弱的测试、构建或 Release 逻辑。发布入口先统一配置持久化 `GOCACHE`：`WECLAW_GOCACHE` 优先，其次保留调用方显式导出的 `GOCACHE`；本机 Darwin 数据盘共享根目录存在时使用项目专属缓存，其他主机回退到 `go env GOCACHE`。

## Core Directories

- `cmd/`：CLI 命令、启动、停止、更新、重启保护、Companion 和发布相关入口；更新后重启与手动重启必须在停止旧服务前复用启动预检。
- `config/`：配置结构、默认值、Agent 探测、工作目录白名单、管理员白名单和 API 安全校验。
- `agent/`：统一 Agent 接口与各类 runtime；`codexauth/`：按 shared-host namespace 隔离的 OAuth profile、系统凭据库/显式文件后端、安全文件与跨进程事务锁。
- `platform/` 提供跨平台消息与回复抽象；`messaging/` 负责命令、会话、审批、结构化进展、任务状态、终态 outbox 和 Agent 调用。
- `observability/`：端到端 Trace 上下文、固定字段事件、轮转 JSONL 存储、受保护查询和 Codex 线协议脱敏录制。
- `feishu/` 负责飞书事件与交互；`wechat/`、`ilink/` 负责微信个人号接入、replier、token 和 monitor。
- `api/` 提供本机 HTTP API；`web/` 提供配置界面；`docs/`、`tasks/` 保存上下文、当前任务和长期 lessons。

## Documentation Map

- `AGENTS.md`：可移植代理入口，只放路由、约束和验证边界。
- `docs/README.md`：文档索引，说明 authority docs、任务记录和验证命令。
- `docs/AI_CONTEXT.md`：当前代码地图和高风险路径摘要。

## High-Risk Areas

- 飞书真实发送者身份和 session routing 必须分离；`platform.IncomingMessage.Route` 是一等会话路由，`feishu_session_key` metadata 仅作卡片载荷与旧调用兼容，迁移期必须双写双读。路由不得替代真实 `UserID` 或发送目标。
- 飞书会话按聊天窗口聚合：DM 使用 `feishu:<tenant>:dm:<chatID>:<senderOpenID>`，群聊使用 `feishu:<tenant>:group:<chatID>`；回复串 / 话题不再生成独立 route。
- 飞书多项目入口通过 `platforms.feishu.bots[]` 配置多个机器人；每个 bot 的凭证按 `weclaw feishu login --name <bot>` 或 `weclaw feishu bootstrap --name <bot>` 保存，`app_secret` 不得写入 `config.json`。飞书与微信账号凭据、微信主动发送所需的 `context_token` 统一通过 `internal/securefile` 读写：目录和文件最终固定为 `0700/0600`、原子替换；读取凭证前可自动收紧当前用户拥有的真实目录和普通文件权限，仍拒绝符号链接、异常 owner、非目录/非普通文件和无法安全修复的状态。损坏或不可读的 token 状态必须阻止对应 adapter 启动，不能静默当成空状态覆盖。共享同一 `WECLAW_HOME` 的微信凭据与 `context_token` 读改写事务统一通过 `internal/accountstore` 的进程内门禁和 Unix advisory lock 串行化；固定的 `accounts/.write.lock` 必须持久保留，不能删除或原子替换。
- `weclaw feishu bootstrap` 只负责首次配置向导：保存凭证、更新 `bots[]`、提示可用 `lark-cli` 做权限/事件诊断；飞书运行时仍使用内置 SDK 长连接，不依赖 `lark-cli`。
- 飞书显式启用时必须配置非空 `bots[]`；缺失 bot 应在 `config.Validate` 阶段 fail-fast，不应等到平台启动阶段才失败。
- 飞书最小权限应覆盖单聊入站、群聊 @ 入站、读取消息资源、发消息、资源、会话、CardKit 和机器人菜单：`im:message.p2p_msg:readonly`、`im:message.group_at_msg:readonly`、`im:message.group_at_msg.include_bot:readonly`、`im:message:readonly`、`im:message:send_as_bot`、`im:resource`、`im:chat`、`cardkit:card:read`、`cardkit:card:write`、`application:bot.basic_info:read`、`application:bot.menu:write`；`user` scopes 可为空。下载图片或文件需要 `im:message:readonly`、`im:message.history:readonly` 或 `im:message` 中至少一个，只有入站事件权限仍会收到消息但无法获取资源。
- 飞书 bot 的 `allowed_users`、`default_agent` 和 `progress` 按 `app_id` 隔离；`allowed_users` 支持应用级 `open_id` 和同开发商下稳定的 `union_id`，多机器人优先配置 `union_id`；新增、删除 bot 或修改 `app_id` 属于平台拓扑变化，需要重启。
- 飞书未授权入站身份会在访问控制前写入 `~/.weclaw/feishu-identities.json`，但不会自动放行；管理员通过 `/feishu users pending/list/approve` 确认后才写入 `config.json`，本地只读查看使用 `weclaw feishu users pending/list`。
- `/progress` 从飞书入口触发时必须按当前 `account_id` 写入账号级配置；普通用户可以查看当前模式，只有 `admin_users` 能修改。广播、Codex 会话切换和共享 host 任务 watcher 也必须读取账号级进度配置。Agent 到 messaging 使用 `agent.ProgressEvent` 传递 kind/state/id/path/sequence，旧字符串 Agent 只能在兼容边界包装；`Handler.tasks` 中的 `taskService.active` 持有活动任务索引，`activeAgentTask.view` 通过纯 reducer 保存唯一任务视图。原生 stream 任务卡的 `stream_timeline_limit` 默认 `0`，表示不设置 WeClaw 条数上限；正数表示只保留最近 N 条，负数配置必须拒绝。该字段按全局、Agent、平台、飞书账号四层合并并允许显式零覆盖；`max_progress_messages` 仍只限制非 stream 消息。stream 时间线条目包括按稳定 ID 语义合并的计划、工具和文件摘要，以及 Codex 明确标记为 `agentMessage.phase=commentary` 的用户可见消息；不包括 `commandExecution` 生命周期、原始协议事件、推理、逐 token、命令输出、工具日志或最终回答。同一语义阶段的运行/完成事件按稳定 ID 原位更新。`ProgressKindCommentary` 必须按来源顺序以完整正文累计进时间线并参与条数限制和自动续卡，不按 180 字符裁剪；Claude 的 `ProgressKindMessage` 继续只更新独立“当前说明”区域、推进事件水位且不占时间线，单条按 180 字符收敛。飞书任务卡在第一条有效非命令进度到达前，正文只能显示 `思考中.....`，定时心跳不得用等待、连接或阶段提示覆盖；Codex commentary、Claude message、计划、文件或工具摘要任一到达后，就展示截至当前的回复与安全结构化进度，并把活跃提示只保留一次在正文底部。命令、内部推理、状态心跳和审批事件不能解除等待态；审批仍使用独立交互与记录区域。飞书活跃任务卡不再额外渲染顶部重复状态行；终态必须移除活跃提示，恢复引用也只保存清理后的过程正文。`/ps` 读取同一 reducer 的最近 display text，旧字符串 Agent 和非 stream 平台保持原有兼容行为。飞书在每次更新前按完整卡片 JSON 的保守字节软上限预检；预计超限时旧卡保留并冻结当前段，先持久化新卡恢复引用，再把审批绑定、后续进展和终态迁移到带连续段号的新卡，不能等待 API 拒绝或静默截断。任务结束时最新卡只把标题或状态收敛为完成、失败或停止并关闭流式状态，必须保留当前分段、审批、时间线和当前说明；两者都不存在时显示明确说明。Codex App Server 的 `turn/plan/updated` 以及 `fileChange`、`mcpToolCall`、`dynamicToolCall` 生命周期必须转换为安全摘要；`commandExecution` 生命周期不投影到进度卡，真正需要用户处理的命令审批仍通过独立 approval 事件展示。命令输出、工具参数、结果、diff 和逐 token 增量不得进入卡片，`final_answer` 和未知阶段只参与最终回答组装。真正需要用户处理的其他权限审批和补充信息仍必须明确展示；内部输出 delta、patch delta、审批审查、guardian 和传输 warning 只在协议层消费或脱敏记录。终态水位线之后的旧 sequence 或晚到 watcher 不得覆盖终态。Codex 窗口切回仍在运行的任务时，只在 frontend binding 真实变化后于消息底部重建任务卡，并以 reducer 最新快照初始化；旧卡进入“已转移”且停止流式，后续进展和终态只能写当前卡，重复选择同一绑定不得重复建卡。独立任务卡可用时，会话切换结果只确认工作空间、模型配置和任务卡位置，不得重复展示任务正文、当前进展或终态回传说明；无任务卡的文本平台继续保留完整摘要。飞书原生 stream 任务卡把稳定的当前摘要放在折叠面板外，把完整进度与当前说明放在 `collapsible_panel` 内；审批记录位于面板之前，使折叠面板成为卡片最后一个内容区域。活动卡默认展开且允许用户手动折叠；收起态以卡片末尾的“展开完整进度”面板标题作为入口，展开态在完整时间线末尾增加“收起完整进度”按钮。该按钮回调只按任务卡 ID 和单调 sequence 更新原 CardKit 卡，不得进入 Agent 命令路由；状态失效或更新失败必须提示用户继续使用原生面板控件。普通进度只更新稳定摘要与详情组件，不全量重建卡片，因此不能重置客户端的展开状态。完成、失败、停止和已转移卡默认折叠。Codex 活动 turn 的每条普通补充输入或成功 `/guide` 都必须在同一 thread 控制锁内完成 runtime 校验、`turn/steer`、reducer 更新和 - `messaging/codex_session_acquire.go:acquireCodexSessionWithBindingLocked` 先准备目标 thread 的当前 provider 兼容状态，再提交当前窗口 binding、持久化窗口 Agent，最后把该 frontend conversation 映射到当前唯一 Host 的 thread。Agent 选择落盘失败时只在 after-image 仍匹配时回滚；runtime 失败保留 durable binding 并明确报告通道暂不可用。历史 Codex thread 的 `model_provider` 不是续写权威；当前 Host 对目标 workspace 生效的 provider 才是权威。绑定前调用 `agent/codex_provider_runtime.go:PrepareCodexThread`，`agent/codex_runtime_turn.go:RunCodexTurn` 在 writer lease 前再次复核。provider 不同时，迁移必须进入 admission、app-server exclusive gate、全局已知 active/unknown thread、writer lease 与 Host lifecycle 门禁；只修改目标 thread 的 rollout、`state_5.sqlite.threads` 行和可选 `local_thread_catalog` 行，保留 thread ID、用户消息、可见助手回复、工具调用与结果，删除 provider 专属的加密 reasoning/compaction 状态，并修复所有层级的已知 Responses item ID 及引用。每次迁移在 `CODEX_HOME/backups/weclaw-provider-migration/` 写入 `0600` 原始 rollout 和阶段 manifest；存储提交前失败应按 before-image 回滚，resume 交付不确定后不得在可能已加载的 thread 下反向覆盖文件，而要把运行通道置为不可写等待复核。共享 Host 重启后必须以 `config/read(cwd)` 和显式 `thread/resume.modelProvider` 双重核验；Desktop Host 读取同一配置层、受控重启并重载目标历史。active 目标不被中断，当前 turn 的 steer 沿用其既有 provider；下一个新 turn 必须先迁移。
- `agent/codex_runtime_lease.go` 只把当前 Host 级权威运行态（`weclaw` 或 `desktop`）视为可写，同一 thread 同时只允许一个新 turn writer lease；route、窗口或旧 owner revision 不参与生产多 frontend 写入授权。已有活动 turn 时，其他前端的普通输入通过 `turn/steer` 直接进入同一 turn，不创建私有 pending queue 或第二 lease。全局输入顺序从 app-server 接受请求开始；Desktop/CLI 尚未发送的 queued follow-up 只是客户端草稿。turn 接受后观察通道断线必须保留 uncertain lease，只有权威 Host 的终态证据才能释放；非权威 Host 的晚到广播不得生成事件、改写 binding 或清除 lease。
- `/cx` 是 Codex 会话命令专用命名空间，未知子命令统一返回 `/cx help`；Codex 消息使用 `/codex <内容>` 或 `@cx <内容>`。`/cx owner` 及其旧参数已删除；`/cx status` 正常态只紧凑展示工作空间短名、会话、任务、账号标签和运行状态，Desktop 模式显示 `Codex App`。`/cx app`、`/cx cli`、`/cx attach`、`/cx detach` 继续拒绝从消息端启动本机进程；本机终端入口是 `weclaw codex cli`。旧 Codex Companion 和原生 `type: cli` 配置迁移到共享 ACP app-server，`codex exec` 独立会话模式明确停用。App Host 的 follower IPC 支持已有 thread 的历史、turn、steer、interrupt、审批、用户输入、thread settings 和按 connection epoch 同步的 queued follow-up 草稿；草稿不能生成 writer lease、WeClaw pending task 或已接受输入。Desktop follower 不暴露 thread/start、archive、model/list、账号与额度接口，因此这些操作必须明确提示在 Codex App 执行，`/cx new` 失败时不得删除当前 binding。`/model`、`/reasoning` 在已有 App thread 上使用 `thread-follower-update-thread-settings`，共享 Host 继续使用 `thread/settings/update`；未知能力不得静默降级。`/cx rename current|<编号> <名称>` 只通过 shared app-server 的 `thread/name/set` 修改 Agent 全局 thread 名称，并以第二次 `thread/read.name` 精确读回为成功依据；Desktop follower 没有该写能力时提示在 Codex App 内执行，禁止为重命名启动第二个 Host。消息层在 binding 锁内解析可访问且未隐藏的目标，再按 thread control 和 writer 门禁拒绝 active/unknown 任务；RPC 已发送但响应或读回无法确认时保留全部 binding 并返回未知结果，审计只记录脱敏 thread ID，不记录名称。
- Claude 运行拓扑是单一进程驻留 ClaudeHost、多前端 binding：一个 WeClaw 服务只创建一个 Claude `ACPAgent` 和一个 `claude-agent-acp` 子进程，子进程生命周期由服务显式 `Stop` 或真实退出管理，不能继承触发启动的单次消息 context。标准 ACP `readLoop` 是 `Cmd.Wait` 的唯一所有者，自然 EOF、启动失败和显式 Stop 都必须等待同一个完成信号，禁止清空 `cmd` 后遗留 zombie 或重复 Wait。当前上游 adapter 使用 stdio ACP，因此前端通过 WeClaw 服务复用该 host；不要虚构或暴露未经实现的 Claude Unix socket 协议。`weclaw doctor` 的 Claude ACP 成功项只验证 `initialize`，不得声称已经探测 `session/list` 或 `session/resume`。
- `weclaw doctor` 默认只读，并按配置相关性区分阻断与可选依赖：检查 `sqlite3`、Linux `bubblewrap`、Codex `app-server`、Node.js/npm、Claude CLI 与固定版本 ACP adapter。`doctor --fix` 的 Codex 组件使用 OpenAI 官方 standalone 安装脚本，不依赖 Node.js/npm；Node.js/npm 只为 Claude 与 ACP adapter 展开。安装器先下载到独立临时文件，再以固定参数和 `CODEX_NON_INTERACTIVE=1` 执行，不通过动态 shell 拼接。其余组件只安装用户选中的缺失项，并用角色标签区分可选增强、Agent、安装前置和 Claude 必需 adapter；非交互模式必须同时提供 `--components` 与 `--yes`。首次 `install.sh` 安装在二进制校验后先运行只读 Doctor，有控制终端时通过 `/dev/tty` 进入同一选择向导，无终端时只打印显式后续命令；不得恢复“检测到 Claude 就自动安装 ACP”的旧副作用。系统包只允许固定参数的 `apt-get`、`dnf` 或 Homebrew，npm 安装禁止 `sudo` 和动态 shell 拼接；非 root Agent 二进制固定安装到 `~/.local/bin`，只在修复进程内临时扩展 PATH，重检通过后保存绝对路径并恢复原 PATH。账号登录不属于自动修复范围。
- `session/list` 是 Claude 目录事实源；`claudeSessionStore` v4 只持久化 route 到 workspace/session 的 binding、状态和单调 revision，v1-v3 的 `remote`、`local`、`unclaimed` control intent 加载后必须丢弃并重写。多个飞书或微信窗口可以绑定同一 session，不能互相释放或覆盖 binding；`ACPAgent.UseClaudeSession` 发现目标 session 已在当前 host generation 恢复时只提交 frontend conversation 映射，不得再次发送 `session/resume` 创建第二个 host-side session。
- Claude 的 `/cc switch`、`/cc new`、飞书会话卡片和默认 Claude 的全局 `/new` 都复用 binding-only acquire：先 CAS 提交当前 route binding，再持久化窗口 Agent，最后恢复共享 runtime。Agent 选择落盘失败只在 after-image 仍匹配时回滚；`session/resume` 或 ClaudeHost 失败保留新 binding 并记为 `resume_failed`，普通消息 fail-closed，但其他 route 的 binding 不受影响。重启加载后的有效 binding 统一为 `pending_resume`，首次真实使用恢复 runtime。
- Claude prompt 只按 `claudeSessionExecutionKey(sessionID)` 获取 session writer lease。`Handler.tasks` 的活动任务索引中，同一 session 槽位只允许一个 route 启动任务；同 route 最多排队一条续跑消息，其他 route 必须收到明确 busy 且不能把消息写入当前任务队列。任务登记前保存 binding session/revision 快照，prompt 前重验；route 自己切换或 `/cwd` 不能在其任务运行时改变 binding。Complete、Fail、Stop 和 Cancel 最终仍通过同一 active task 生命周期释放 lease。
- `/cc owner` 和 `/cc cli` 已停用，帮助与飞书卡片不得广告这两个入口；独立 `claude --resume` 会绕过共享 session writer lease，禁止重新引入 Claude CLI 聊天或本地交接。`AgentInfo.LocalCommand` 仅保留给 `/cc quota` 的短生命周期、无提示词额度查询回退：优先兼容 Claude Code 旧版 `Claude Code-credentials` Keychain 或 `CLAUDE_CONFIG_DIR/.credentials.json`（兼容 `claudeAiOauth`、`claude.ai_oauth`），只把内存中的 access token 发送到固定 Anthropic OAuth usage 地址；凭据不可读或请求失败时，原生进程只发送 `initialize`、`get_usage`。两条路径都不得记录/持久化 token、回显响应体、跟随重定向、扫描 transcript 或发送模型提示词。
- `/cc new` 后尚未进入 ACP 目录的空会话，只能由 `/cc ls` 从同 route 的 ready binding 暂态投影展示，不得进入 `/cc switch` 候选或绕过 `session/list` 校验。`/model`、`/reasoning` 在 ready session 上通过 ACP `session/set_config_option` 修改当前 session 并从下一轮任务生效；无 ready binding 时修改新 session 默认值，`/cc model status` 只展示默认值且同时显示 model 与 effort，`/cc model reset` 清除新 session 的显式默认配置。新 session 默认值不在 ACP 公布的选项内时必须保留原绑定、返回可操作错误，禁止静默降级。飞书设置卡必须携带生成时的 session ID，并在 binding 锁内重验，旧卡不得写入新 session。`/cc rename current|<编号> <名称>` 通过现有单一 ClaudeHost 加载目标 session，并且只有该 session 最新的 ACP `available_commands_update` 完整快照合法且包含严格命令名 `rename` 时，才在目标 session writer lease 下发送唯一文本 `/rename <名称>`；不得按 adapter 版本猜测能力或启动独立 Claude CLI。Host generation 更新时清空已加载 session、命令和标题缓存；控制 prompt 发送后必须以 `session/list.title` 精确读回为成功依据，失败或不一致返回未知结果并保留所有 frontend binding。审计只记录脱敏 session ID，不记录名称或 prompt。
- Claude ACP 复用通用后台任务队列：每个活动任务最多暂存一条同 route 消息，失败后仍自动续跑；`/cancel` 撤回暂存，`/stop` 按当前窗口 Agent 停止，`/guide` 对 Claude 明确不支持。
- 微信 / 飞书显式绑定到当前权威 Host 中正在运行的会话后，WeClaw 会读取 thread 状态、登记 active task observer；普通消息立即 steer 到该活动 turn，完成后回推结果，不再先进入 WeClaw 私有续跑队列。
- 运行中任务登记在 `Handler.tasks` 所有的 `taskService.active` 索引；`restart` 和 `update --restart` 必须先通过 loopback `/api/runtime/drain` 原子关闭 admission，普通模式遇到 active task 时恢复 admission 并拒绝，`--force` 才取消任务并有界等待终态。systemd 运行态必须委派固定 `weclaw.service`，不得停止后另起后台 daemon；SIGTERM 先排空任务再取消平台注册表，超时遗留卡由下次启动的 outbox 恢复。普通 `weclaw update` 不得隐式重启。
- 微信 / 飞书远程管理命令由 `messaging/admin_commands.go` 执行 WeClaw 自身命令，不应进入 Codex / Claude；必须先校验顶层 `admin_users`，且管理员也必须在平台 `allowed_users` 内。飞书管理员身份只接受跨应用稳定的 `union_id`，`/update` 与 `/restart` 还必须在可证明的私聊窗口执行。支持流式卡片的平台执行 `/update` 时必须在同一卡片内从版本检查收敛到“已是最新版本 / 更新成功 / 失败”终态；`/restart` 必须在旧进程保存 CardKit 卡片引用后才释放延迟启动，启动失败时由仍在运行的旧进程删除待完成记录并把原卡收敛为失败，新进程确认恢复后才回写同卡成功终态，直接更新失败才把固定 checkpoint 交给 terminal outbox 重试。不支持流式卡片的平台降级为先回复后台受理、结束后另发最终结果。`/update` 摘要必须识别 CLI 当前使用的中文版本输出。群聊 `/mode yolo` 按真实操作者和 route 的组合键隔离，不能让同群其他成员继承自动审批；切换时先按既有幂等门禁放行该范围内的 pending approval，再把已发飞书审批卡更新为无按钮的自动批准终态并写入任务卡。CardKit 更新失败只能告警和审计，不得撤销或重复提交 Agent 审批；后续 YOLO 审批不再弹独立审批卡，有任务卡时只追加自动批准记录。
- 微信同一条入站消息触发多次回复时，`wechat.Replier` 必须为后续 `SendText` 生成新的 `client_id`，避免微信端把结果消息按重复消息去重。外部 `ILinkBotID` 写入凭据或 context token 路径前必须统一通过 `ilink.NormalizeAccountID` 编码，不能把 `/`、`\\`、绝对路径或 Unicode 原文直接交给 `filepath.Join`；旧版兼容映射发生文件名碰撞时，保存和加载都必须失败关闭。Web 扫码登录同一服务只允许一个 active poll，新登录必须取消并终态化旧会话，晚到回调不得保存旧凭据或覆盖新状态。
- Agent `permission_level` 省略时等同 `default`；显式配置只接受 `default`、`auto_review`、`full_access`，分别映射 Codex `approvalPolicy`、`sandboxMode` 与 `approvalsReviewer`，旧值必须 fail-fast。`weclaw config permission --agent <name> --level <level>` 会清空三个高级覆盖字段，运行中 Agent 必须重启后生效。`auto_review` 仍是 `workspace-write + on-request`，只把 reviewer 交给 Codex，WeClaw 不会把审查失败转成允许；`full_access` 仍只拥有运行 WeClaw 的操作系统用户本来可访问的范围。聊天 `/mode yolo` 只是当前进程内按操作者与 route 隔离的审批自动允许，不持久化、不改变 sandbox 或权限档位。`codex_host_mode` 只接受 `auto`、`daemon`、`managed`；显式 daemon 禁止自定义 socket 和 `run_as_user`。原生 Codex shared app-server 规范化后默认写入 `codex_auto_update: incompatible`，但只有上游明确报告 schema/version 不兼容且没有 writer lease 时，兼容 managed Host 才能持有生命周期锁调用官方 `codex update`。通用 SQLite 初始化错误、锁争用、损坏、socket 就绪超时、调用方取消、普通进程退出和连接错误不得触发更新；官方 daemon 模式也不得由 WeClaw 更新。更新前后版本必须可验证且真实变化，失败、版本未变或更新后仍无法启动都保持 fail-closed。显式 `off` 永久关闭该行为。
- Web 配置保存必须保留 Agent 的 Codex 权限字段、Host 模式、共享 socket 和更新策略：`permission_level`、`approval_policy`、`approval_reviewer`、`sandbox_mode`、`codex_host_mode`、`app_server_socket`、`codex_auto_update`。
- `api_addr` 监听非 loopback 地址时必须配置 `api_token`；loopback 地址允许留空，但 `weclaw doctor` 必须告警本机其他进程可调用管理接口，不能显示为安全通过。
- 发布后本机更新必须走 GitHub 权威 Release，或在 `darwin/arm64`、`linux/amd64` 上走 Gitee 镜像，并由 `weclaw update` 校验，不要手工覆盖二进制。`update_source`/`WECLAW_UPDATE_SOURCE`/`--source` 支持 `auto`、`github`、`gitee`，命令行优先于环境覆盖后的配置；`auto` 只允许对网络、TLS、超时和 5xx 换源，4xx、非法 tag、摘要缺失/重复/不匹配必须失败关闭，稳定版本不得降级。普通 `weclaw update` 在已是最新版时不得启动 Claude ACP 预检；实际安装新版本或显式 `update --restart` 才执行启动预检。安装新版本时必须保留临时旧二进制直到完成边界提交，预检失败必须恢复旧二进制；`update --restart` 的安全检查、停止或新版本启动失败也必须恢复旧二进制，旧服务已停止则重新启动旧版本，恢复失败必须同时保留原始错误和回滚错误。Codex 用户可见消息投影以显式 `phase=commentary` 为最高优先级；为兼容真实运行时省略 `phase` 的情况，受控 turn 与接管 watcher 必须共同延迟一条已完成消息。后续另一条消息、计划、文件、工具、审批或不含正文的命令活动证明 turn 仍在继续时，上一条才转换为 `ProgressKindCommentary`；正常 `turn/completed` 前仍待判定的最后一条只作为最终回答。命令活动信号不得携带命令、输出或 `ProgressEvent`，也不得解除“命令不展示”的边界。同一消息 ID 的重复快照只更新待判定正文，不得重复追加。
